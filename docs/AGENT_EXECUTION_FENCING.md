# Agent 执行权与会话提交

2026-11-19。任务结果和会话历史由 PostgreSQL 统一保存，Redis 只保存可重建的会话缓存。此改造适用于异步任务、同步对话、SSE 与本人恢复入口，不改变 Java 对交易身份、订单状态和库存的最终校验。

## 执行权

每次领取任务生成新的 `lease_owner`，并递增 `execution_epoch`。执行者上下文保存这两个值、租约长度以及领取时的会话版本。领取与续租使用数据库时间，不依赖实例本机时钟。

任务领取在短事务中锁定会话记录，确认同一会话没有其他有效执行任务，然后读取已提交的最近八轮历史。异步入口继续按共享队列的持久受理顺序运行；同步兼容入口也必须获得相同的会话执行权，但不承诺与异步队列统一 FIFO。

模型调用期间不持有数据库连接或行锁。后台心跳按 `min(10秒,租约长度/3)` 续租，要求执行者、执行版本、运行状态及未过期时间全部匹配。异步工作者还在同一续租事务中校验并延长所属队列租约。租约已过期时不能续活；续租失败会取消当前执行，最终写入仍由数据库条件保护。

事件、检查点与最终结果的写入都校验执行权。旧执行者在新实例接管后、或者自身租约已经过期时，收到 `TASK_LEASE_LOST`，不能写入运行结果。续租不延长整轮工作流超时，也不替代模型调用超时和共享配额。

## 原子提交

### 入队序号与提交顺序

ordinal 本身只是数据库序列，不能单独保证受理顺序。当前异步受理在写入 agent_jobs、分配 ordinal 之前取得 `pg_advisory_xact_lock(hashtextextended('agent-shared-admission',0))`，并一直持有到整个受理事务提交或回滚。因此，前一事务已经分配序号但尚未提交时，后一事务不能越过同一个受理锁去分配下一个队列序号。

当前使用全局受理锁，同时保护全局/每用户队列容量检查。它会让跨会话的短暂入队临界区也串行；跨会话并行描述的是工作流执行阶段，并非所有受理 SQL 都并行。这里的顺序是数据库串行化后的受理顺序，不是客户端发送时刻或 HTTP 回执到达顺序。

回滚仍会留下序号空洞。领取逻辑只排除真实存在且尚未结束的更早队列项，不等待不存在的连续序号。

新增 `tests/customer_agent/test_admission_order.py` 在第一事务分配序号后、提交前设置屏障，观察第二事务在真实 PG advisory lock 上等待，且第三连接看不到第二条队列记录；分别验证第一事务提交后按 T1/T2 领取，以及第一事务回滚后 T2 可以跨过序号空洞领取。连同持锁接管、过期写入及 Redis Lua 版本保护，共6项专项复验通过。

工作流完成后，一个 PostgreSQL 事务执行：

1. 条件更新任务结果，匹配 owner、epoch、运行状态和有效租约。
2. 锁定会话，检查当前执行任务和领取时的会话版本。
3. 写入 `agent_turns`，以 `task_id` 为唯一键。
4. 推进会话 revision，写入缓存更新 Outbox。
5. 释放会话执行权，写入完成事件。

上述操作一起提交或回滚。数据库响应不明时，客户端继续使用原请求编号/任务编号查询，不凭 Redis 是否有新回答判断成败。任务完成而队列尚未确认时，后续工作者读取终态结束队列记录，不重新推理。

补充条件或恢复同一任务时更新原逻辑对话轮，不追加第二条相同 task_id 的回答；保留原问题及补充信息。已完成任务的“继续/恢复/重试”直接返回已提交结果；新问题应创建新任务。

## 缓存更新

`agent_session_cache_outbox` 以用户与会话为键，合并到最新 revision。更新任务与回答处于同一事务，缓存暂时不可用不会撤销已提交的回答。

多个实例通过短租约和 `SKIP LOCKED` 领取缓存更新任务，数据库连接释放后才访问 Redis。更新任务只保存会话标识和版本，不保存一份可能过期的历史；执行时读取 PostgreSQL 最新快照。

Redis Lua 原子比较会话 revision，只允许较新版本覆盖旧版本。版本按十进制字符串长度和字典序比较，避免 BIGINT 在 Lua 数值转换时丢失精度。缓存缺失时同样从数据库读取最新快照，不直接重放旧通知中的内容。

Outbox 确认同时匹配执行者与已处理 revision。写缓存期间若又提交了新一轮，旧确认不能删掉新版本的更新任务。失败保留记录并退避重试，进程退出后由租约到期接管。

会话查询先在 PostgreSQL 校验用户归属和当前 revision，只有缓存版本一致时才返回缓存；缓存缺失、旧版本、格式异常或读失败均回源。工作流领取时始终重新读取数据库历史，缓存不决定执行顺序或执行权。

## 交易操作

同一任务准备同一交易操作时，使用由 task_id、操作类型和目标生成的稳定幂等编号，不将执行版本放入业务幂等键。恢复时复用原操作记录；准备动作的数据库写入也校验任务执行权。

用户确认后，操作记录以条件更新从 prepared 转入 running。重复确认不再次提交业务 POST；网络结果不明继续核对，不自动重发。Java 仍校验本人、订单状态、一人一券和库存条件。

## 事务持锁与故障接管

结果提交首先执行匹配执行者、epoch、运行状态和未过期时间的 `UPDATE ... RETURNING`；没有返回行即拒绝，返回一行才继续同一事务中的会话、事件和 Outbox 写入。条件更新获取的任务行锁一直持有到提交或回滚。B 不能因为租约时间经过就绕过 A 的数据库行锁；在 Read Committed 下等待结束后重新判断更新条件，已经完成的任务不再通过异步领取条件。

模型请求、Java HTTP 和 Redis 更新均在该提交事务之外。状态库连接设置 `lock_timeout=3s`、`statement_timeout=5s`、`idle_in_transaction_session_timeout=5s`：分别限制等锁、单条 SQL，以及持有未结束事务却不再发 SQL 的客户端会话。等锁超时只取消等待者；闲置事务超时会终止持锁会话并回滚，释放行锁。上述配置不是整个多语句事务的总时长上限。

会话顺序由共享队列的 ordinal 与队头排除条件保证，同一会话仍有更早 queued/running/reauth_required 任务时，不能领取后续任务。`SKIP LOCKED` 只用于避免多个领取者卡在相同行，不能代替队头条件。会话表的 active_task_id 和领取时行锁另外防止不同执行入口同时进入同一会话。

新增回归在真实提交事务更新任务行后暂停，验证另一个连接不能推进 epoch；另一个用例让持锁客户端进入闲置，验证数据库终止连接后事务回滚、行锁释放，再按有效条件接管。

## 升级

- 启动前停止旧版本写入实例，再部署新版本；不混跑使用 Redis 保存最终历史的旧工作者。
- 使用现有状态库自动执行 schema v3 迁移，保留原数据和凭据，不需要删除数据卷。
- 新增任务 execution_epoch、持久会话、逻辑对话轮与缓存更新表；从旧任务表中已经持久化的回答回填历史。不将旧 Redis 中可能未提交的快照直接导入。
- 重复启动只读取版本，不重复执行迁移。旧离线 SQLite 导入后的会话在首次访问时从已导入任务回答补建。
- Redis 会话缓存仍保留24小时；缓存过期不等于删除持久会话。持久数据清理应沿用业务的数据保留策略。
